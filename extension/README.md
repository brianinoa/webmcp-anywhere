# WebMCP Anywhere — Chrome extension

Manifest V3 extension that registers WebMCP tools (`document.modelContext.registerTool`) on every page:
nine generic tools (`describe_page`, `find_text`, `scroll_to`, `click`, `fill_field`, `select_option`,
`submit_form`, `navigate`, `go_back`) plus per-site recipe tools loaded from the bundled `recipes/*.json`
and from the worker's `/api/sync`.

## Build

```sh
pnpm install                                     # repo root
pnpm --filter @webmcp-anywhere/extension build   # -> extension/dist
pnpm --filter @webmcp-anywhere/extension dev     # same, but rebuilds on change
pnpm --filter @webmcp-anywhere/extension typecheck
pnpm --filter @webmcp-anywhere/extension test    # vitest + jsdom
```

The build is plain Vite driven by `scripts/build.mjs`: each of `main-world.ts`, `content.ts` and
`background.ts` becomes one self-contained IIFE (content scripts can't share chunks), `popup.html` is a
normal Vite HTML build, and `manifest.json` + `public/` are copied over. Icons are generated by
`node scripts/make-icons.mjs` (already checked in under `public/icons`).

## Load unpacked

1. Open `chrome://extensions`, enable **Developer mode**.
2. **Load unpacked** → pick `extension/dist`.
3. After every rebuild press the reload icon on the extension card (and reload the page).

## Enable WebMCP in Chrome

WebMCP ships behind a flag in Chrome 149+:

1. Go to `chrome://flags/#enable-webmcp-testing`, set it to **Enabled**, relaunch.
2. Verify on any page: open DevTools and run `document.modelContext` — it should be an object, not
   `undefined`. If it is undefined the extension logs a hint
   (`[WebMCP Anywhere] document.modelContext is not available…`) and the badge shows **WebMCP off**.

### See the tools in the Model Context Tool Inspector

1. Install Google's **Model Context Tool Inspector** extension (from the WebMCP developer docs /
   Chrome Web Store) alongside this one.
2. Open a page, then open the inspector from its toolbar icon. You should see the nine generic tools and,
   on matching sites (e.g. youtube.com, wikipedia.org), the recipe tools. Select a tool, fill in its
   input JSON and **Execute** — the result is the same short JSON string an agent gets.
3. Tools tagged `sensitive` (and `write` tools if you enabled "Also ask before write tools") pop an
   approve/deny card in the in-page badge; the call resolves only after you click **Approve**
   (60 s timeout).

### See the tools in the ChatGPT desktop app browser

The ChatGPT desktop app's built-in browser is Chromium-based, consumes WebMCP natively and supports
extensions:

1. In the ChatGPT app, open the browser, then its extensions page (`chrome://extensions` in the address
   bar), enable Developer mode and **Load unpacked** → `extension/dist`.
2. Navigate to any site. The address bar shows a **Site tools** indicator once tools are registered —
   click it to list them. Our badge (bottom-right pill "⚡ N tools") shows the same list.
3. Ask ChatGPT to act on the page ("describe this page", "search for X", "play the video"); it will
   call the tools and the badge's activity log shows each call, input, result and duration.

## In-page badge

A small pill in the bottom-right corner (closed Shadow DOM, no page CSS leakage). Click it to see:

- registered tools with a sensitivity chip (`read` / `write` / `sensitive`) and recipe id,
- a live call log (tool, input summary, result or error, milliseconds),
- approval cards for sensitive calls with the pretty-printed input.

Hide it with the **Show in-page badge** setting; approvals then fall back to a native `confirm()`.

## Settings (popup)

| Setting | Default | Meaning |
|---|---|---|
| Worker API base | `http://localhost:8787` | Where recipes are synced from (`GET /api/sync`). |
| Ask before sensitive tools | on | `submit_form`, `navigate`, and recipe tools marked `sensitive`. |
| Also ask before write tools | off | `click`, `fill_field`, `select_option`, `go_back`, recipe `write` tools. |
| Show in-page badge | on | Toggle the floating pill. |

Settings live in `chrome.storage.sync`. Recipes are cached in `chrome.storage.local`, re-synced every
10 minutes by a `chrome.alarms` alarm, on **Sync recipes now**, and whenever the API base changes. If
the worker is unreachable the cache is used, and bundled recipes are always available. Remote recipes
that contain `js` actions are dropped — only bundled first-party recipes may run JS.

## Architecture

```
page (MAIN world)          ISOLATED content script            background SW
main-world.ts  <-postMessage->  content.ts  <-chrome.runtime->  background.ts  <- popup.ts
 - registerTool()             - settings/recipes bridge          - per-tab state + call log
 - generic tools              - badge (Shadow DOM)               - recipe sync + alarm
 - recipe tools via runner    - approval UI
 - invoke() pipeline
```

`invoke()` wraps every tool: posts `tool-call`, waits for approval when needed, runs the tool, posts
`tool-result` with the duration, and returns a short JSON string. SPA navigations
(`pushState`/`replaceState`/`popstate`/`hashchange` + a debounced MutationObserver) re-evaluate which
recipe tools match the URL and (un)register accordingly.
